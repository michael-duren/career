# Developer guide

Career is one Go service that serves the static Astro build and the `/api` routes, backed by
PostgreSQL. Leetgrinder pages are rendered on the server with templ.

## Prerequisites

- Node.js (see `.github/workflows/ci.yaml` for the CI version) and npm
- Go (version from `go.mod`)
- Docker with Compose v2

## Getting started

```sh
make dev
```

`make dev` installs dependencies, sets up `.env`, starts PostgreSQL, builds the frontend,
applies migrations, and starts the Go server. Open http://localhost:8080 and log in with
`admin` / `password123` if you accepted the local defaults.

`make start` does the same but skips steps that are already done, and also starts the local
observability stack (set `SKIP_OTEL=1` to skip it). Run `make help` for every target.

## Configuration

Run `npm ci` and `npm run setup` to create `.env`. Press Enter to use the local login
`admin` / `password123`, or answer `n` to choose a username and password. The script hashes
the password, generates a random JWT secret, and uses the local Docker Compose database
credentials. Existing `.env` files are kept. For no prompts, use `npm run setup -- --defaults`.
Copying `.env.example` also works, with the same login and a fixed development JWT secret.

`.env.example` documents every setting. The core ones are `APP_ENV`, `DATABASE_URL`,
`AUTH_USERNAME`, `AUTH_PASSWORD_HASH`, `JWT_SECRET`, `PUBLIC_ORIGIN`, `LISTEN_ADDR` and
`STATIC_DIR`. The Go executable reads `.env` without overwriting the process environment.
Development defaults are loopback-only. Production must supply the database URL, listen
address, username, public origin, bcrypt password hash and a non-placeholder JWT secret of at
least 32 characters.

Optional features have their own settings:

- Leetgrinder: `LEETGRINDER_SECRET_KEY`, `ANTHROPIC_API_KEY`, `LEETGRINDER_ANALYSIS_*` (see [Leetgrinder](leetgrinder.md))
- Weekly scheduler Google Calendar: `SCHEDULER_GOOGLE_*`, `SCHEDULER_SECRET_KEY` (see [Weekly scheduler](weekly-scheduler.md))
- Audio thought transcription: `RUNNING_TRANSCRIBE_ENABLED`, `WHISPER_*` (see [running notes deployment](../deploy/running/README.md))
- Metrics: `OTEL_*`

To generate a bcrypt hash without putting a password in shell history:

```sh
read -rs 'password?Login password: '
printf '%s' "$password" | go run ./cmd/api hash-password
unset password
```

Put the output in `.env` as a **single-quoted** `AUTH_PASSWORD_HASH` to preserve its dollar
signs. An unset development hash disables login; a malformed hash is a startup error.

## Running locally

### Database

```sh
make postgres-up migrate check-db
```

PostgreSQL binds only to `127.0.0.1:5433`, with database and user `career_dev` and the
local-only password `career_dev_local`. The named Docker volume persists across restarts and
`docker compose down`. A custom `POSTGRES_LOCAL_PORT` also needs a matching `DATABASE_URL`.

Startup fails with a clear error if migrations have not been applied; the server never changes
the schema or seeds data on its own. Run `make migrate` after pulling new migrations.

### Server and frontend

```sh
npm run build   # builds the Astro site into dist/
make go-dev     # applies migrations and serves on :8080
```

Go serves both the APIs and the static build from `STATIC_DIR`. `npm run dev` runs the Astro
dev server for frontend-only work; build and run Go to test authenticated API calls.
`make watch` runs Go with live reload via Air.

Leetgrinder templates are generated by `make generate` (`go tool templ generate`). `make dev`,
`make build` and Docker builds run it for you. Generated `*_templ.go` files are ignored, so
run `make generate` before `go test ./...` in a fresh checkout.

### Health checks

`/healthz` reports process liveness. `/readyz` checks PostgreSQL and schema compatibility and
returns 503 during a database outage without exiting. `/health` is a readiness alias.

### Observability

```sh
make otel-up   # Alloy (OTLP :4317) -> Prometheus (:9090) -> Grafana (:3000)
```

`make otel-up-local` and `make alloy-local` run the same stack with Alloy built on the host.

## Testing

```sh
make test           # Go tests
make test-postgres  # Go race tests against local PostgreSQL
npm test            # TypeScript unit tests and extension tests
npm run tc          # Astro sync and TypeScript check
npm run test:e2e    # Playwright against an already running server
npm run test:visual # screenshot tests, in Docker (see below)
```

Playwright does not start the app. Point it at a disposable, migrated workspace with
`TEST_BASE_URL` (default `http://127.0.0.1:4337`), `AUTH_USERNAME` and `TEST_AUTH_PASSWORD`.

### Visual regression tests

`tests/visual` screenshots every page at 1280×800 and 390×844 in all four themes and
compares each against its PNG in `tests/visual/__screenshots__` pixel for pixel. It has its
own config (`playwright.visual.config.ts`), so `npm run test:e2e` never runs it.

Always run it through `npm run test:visual` (`scripts/visual-tests.sh`), which CI runs too.
The script starts a throwaway `postgres:18` container, migrates it, seeds it from
`tests/visual/workspace.json`, builds the frontend and the Go server from your checkout,
and runs Playwright inside `mcr.microsoft.com/playwright:v<version>-noble` (the installed
`@playwright/test` version). Text rendering depends on the OS, fonts and Chromium build,
so baselines made by a Playwright on your own machine would not match CI. It needs Docker
with host networking (Linux), Go and Node. Extra arguments go to Playwright.

The pages are made deterministic rather than compared loosely: the browser clock is
frozen at Wednesday 2026-11-18 10:30 in America/Chicago (the fixture's dates are relative
to that day), requests that leave the app are blocked, company logos answer 404 (so they
show initials), and each shot waits for data, fonts and images with motion reduced. The
server keeps its real clock: the fixture's schedule week and history are in the past and
it has no Leetgrinder attempts (the server dates those itself), so the server sees the same
state whatever day the suite runs. Don't add data the server dates by today; a region that
shows the server's own date would need a `mask`. Each shot is the full page: the viewport grows to the page's height, so the
phone tab bar sits at the bottom.

To update the baselines after an intended UI change, or after a Playwright upgrade:

```sh
npm run test:visual -- --update-snapshots           # every page
npm run test:visual -- --update-snapshots -g books  # only matching tests
```

Look at the changed PNGs (`git diff --stat`, then open them) before committing. When a run
fails, `test-results-visual/` holds the expected, actual and diff images; in CI they and the
HTML report (`playwright-report-visual/`) are in the `visual-report` artifact. Changing `workspace.json` changes most screenshots,
so update the baselines in the same commit.

`tests/e2e/modules-off.spec.ts` (part of `npm run test:e2e`) checks that turning a module off
makes its pages and API answer 404, along with every module that depends on it.

Feature-specific suites:

- Leetgrinder extension: `cd extension/leetgrinder && node --test`
- Weekly scheduler: [testing the weekly scheduler](testing-weekly-scheduler.md)
- HTTP smoke test: `go build -o /tmp/career-migration ./cmd/api && node tests/go-api.integration.mjs`
  (uses port 8088 and temporary credentials, creates and removes one synthetic note)

CI (`.github/workflows/ci.yaml`) runs the Go, npm and Playwright suites on pull requests and pushes to `main`.
The Go tests run with `-race` against a PostgreSQL service with `TEST_DATABASE_URL` set, and the job fails if any
database-backed test skips. Each such test creates and drops its own schema.

## Data import and export

```sh
(umask 077; go run ./cmd/api export > .migration-private/export.json)
go run ./cmd/api import --file <path> --source-store <store> --source-key <key> --source-revision '<etag>' --dry-run
```

Export streams the whole workspace as JSON under one consistent snapshot; check the exit status
before trusting it. `GET /api/export` does the same over HTTP but is bound by the 30-second
write timeout, so use the CLI for large backups. Export does not include audio clips, which live
only in PostgreSQL; keep database backups for a full restore.

Import only targets an **empty** workspace and rejects a populated one. Drop `--dry-run` only
for the intended target. It archives the source bytes in a private directory, validates every
entity, and writes everything in one transaction. `.migration-private/` is git-ignored.

`make rebuild-projections` recomputes book and company summaries from their Markdown.

## API

All routes except login and health checks require the session cookie. Mutations require the
exact configured `Origin` and a JSON content type.

- `POST /api/auth/login` with `{ "username", "password" }` sets an HttpOnly, SameSite=Lax
  cookie with a 24-hour lifetime. `GET /api/auth/verify` checks it; `POST /api/auth/logout`
  clears it. Login attempts are rate limited per peer address.
- `GET /api/entries/{kind}` lists (`limit`, `offset`) or reads one entry (`id`). `kind` is
  `note`, `document`, `personal`, `week`, `book`, `company` or `goal`.
- `POST /api/entries/{kind}` with `{ entry, revision }` saves; a null revision inserts.
  Mismatched revisions return 409.
- `DELETE /api/entries/{kind}` with `{ id, revision }` deletes.
- `POST /api/entries/{kind}/toggle` toggles a Markdown checklist item on a book or company.
- `POST /api/goals/steps/move` reorders or moves a goal step.
- `GET /api/agent-context`, `GET /api/export`.
- `GET /api/search?q=` (2–200 bytes after trimming, matched literally, optional `kind`) is the global
  search: `{ results: [{ kind, id, title, module, context, excerpt, titleMatch }], totals: { <kind>: n } }`.
  Up to 5 results per kind, title matches first; `totals` counts every match. Kinds are the entry
  kinds (`goal` included) plus `session` (the next planned, not yet ended session of each scheduled
  title) and `problem` (Leetgrinder). Turned-off modules are left out; an unknown `kind` is 400.
- `GET /api/companies/logo?domain=<host>` returns a company's favicon as a PNG mask (black pixels,
  alpha = the logo shape) that the Companies page paints in `--ink`. The server fetches the icon from
  Google's favicon service (only the host name is sent), removes its background, and caches the result
  in memory for 7 days (a domain with no usable icon for 6 hours, a failed fetch for 5 minutes). It
  answers 404 (browser-cached for an hour) when there is no usable icon, 502 (not cached, logged) when
  the service fails or rate-limits, 400 for anything but a DNS host name, and 404 like the rest of
  Companies while that module is off. The page shows a monogram for anything but a logo.
- `GET /api/counts` returns `{ counts: { <moduleId>: n } }`: saved entries per usable module that
  owns entry kinds (0 when none are saved; Journal sums weekly logs and personal entries), and saved
  attempts for Leetgrinder. Schedule and Agents are left out. Turned-off modules are left out unless
  `?all=1` is passed. The phone More page shows them; Settings → Modules uses `?all=1` for "paused · N kept".
- `GET /api/settings` returns `{ modules, moduleOrder, theme, setupCompletedAt, effective }`.
  `PATCH /api/settings` changes any of `modules`, `moduleOrder`, `theme` and `setupCompletedAt`
  (camelCase here; the spec's `module_order`/`setup_completed_at` are the column names).
  Settings → Modules (`/settings/modules`) sets `modules` and `moduleOrder`; Settings → Theme sets `theme`. It returns 400 for unknown modules,
  unknown or repeated ids in `moduleOrder` (an empty `moduleOrder` resets it to the default), unknown themes, a `setupCompletedAt` that is
  neither an RFC 3339 time nor null, or newly turning on a module whose dependency is off. `effective` says which modules can be used once their dependencies are applied.

### Modules

Every feature is a module, except Home, Search, Settings, Setup and pages, which are always on.
Schedule and Agents depend on Timeline, so they are unusable while it is off. The registry is `src/lib/modules.ts`, mirrored in
`internal/modules/modules.go`; see [the redesign spec](redesign/modules.md). While a module is
off:

- Its pages and API routes return 404. API routes answer `{"error": "<Module> is turned off…"}`
  (or "<Module> needs <Dependency>…"), and so does the Leetgrinder extension.
- Its MCP tools are not listed and refuse calls. Entry tools refuse its kinds. Search,
  `get_career_overview` and `/api/agent-context` leave out its entries.
- People's company tools (`list_connection_companies`, `add_companies_to_queue`) and the
  catch-up queue API (`/api/connections/queue`) also need Companies. Pages hide parts that need another
  module: Companies hides connections without People, journal goal hours need Schedule.
  The journal Markdown views of `/api/agent-context` need Journal (or Audio), not Agents.
- Leetgrinder reminders and the scheduler's background work pause.

Pages (`/documents/*`, the `document` kind, `page` in MCP) belong to no module and are always
on. A turned-off module keeps its data, and `GET /api/export` still includes everything. A module missing from the
stored settings counts as on. If the settings cannot be read, guarded routes return 503
instead of guessing. The settings migration keeps every module on and marks setup done for
any install that was already migrated. A new database still needs setup: after login, a null
`setupCompletedAt` sends the user to `/setup` (first-run setup), which Settings → General can run again.

### Catch-up queue

A connection's `stage` (`to_contact`, `messaged`, `follow_up`, `referral_ask`, or absent when the
person is not queued) and `snoozedUntil` are ordinary connection fields, so they come back from
`GET /api/connections`, survive export/import and LinkedIn re-imports, and can be set through
`POST /api/entries/connection` or MCP `update_career_entry`. A snooze needs a stage; saving without
a stage drops it. The queue endpoints below need People and Companies. The connection changes take
the connection's `id` and the `revision` it was read at (409 when stale, 404 when the person is
gone). "Today" and "this week" (Monday to Sunday) use the weekly scheduler's time zone, which the
browser sets the first time the scheduler is opened; until then it is UTC.

- `GET /api/connections/queue`: `{today, week: {start, end, sent, target}, connections, revisions}`,
  everyone with a stage, snoozed people included (`snoozedUntil` after `today`), ordered by stage
  then name. The server does not limit who can be queued. The UI offers people at board companies:
  `GET /api/connections?linked=1`, minus those that already have a `stage` (the client filters).
- `POST /api/connections/queue` `{id, revision, stage}` adds someone or moves them to a stage and
  clears any snooze. Returns `{entry, revision}`.
- `DELETE /api/connections/queue` `{id, revision}` takes a queued person out (400 if not queued).
  Returns `{entry, revision}`.
- `POST /api/connections/queue/sent` `{id, revision}` records a message: last contact becomes
  today (never earlier than it was), the person moves to the next stage (after `referral_ask` they
  leave the queue), the snooze clears, and the send counts toward this week. Returns
  `{entry, revision, week}`. 400 when the person is not queued.
- `POST /api/connections/queue/snooze` `{id, revision, until}` hides a queued person until `until`,
  a date after today and at most 365 days ahead. Returns `{entry, revision}`.
- `PATCH /api/connections/queue/settings` `{weeklyTarget}` sets the weekly target (1-50, default
  2) and returns `{week}`.

Only "sent" counts toward the week; editing `stage` or `lastContactedOn` directly does not. Sends
are not part of `GET /api/export`.

The Catch-up tab (`src/components/CatchUpBoard.tsx`) links one timeline goal to its strip through goal
metadata (the goal metadata key `catchUpQueue`, `CATCH_UP_GOAL_KEY` in `src/lib/connections.ts`, saved with `POST /api/goals`); linking another goal removes the key from the
old one. Message drafts live in `localStorage` (`career-catch-up-draft:<id>`) and are cleared by
"sent". The older `queued` flag and cadence (the cadence helper `catchUpQueue()` in `src/lib/connections.ts`, unrelated to the goal key) still drive
the "Due for a catch-up" list under the board; the People tab's Queue button now uses the stage queue.

Leetgrinder, weekly scheduler, connections and audio thought endpoints are described in their
feature docs. The MCP endpoint is described in [MCP](mcp/README.md).

## Releases

Production runs on the homelab k3s cluster, managed by Argo CD from the `home-infra` repository.

1. Push a stable tag (`v1`, `v1.2` or `v1.2.3`) on a commit on `main`, or publish a release.
2. `.github/workflows/release.yml` verifies the tag, reruns the tests, publishes
   `ghcr.io/michael-duren/career:sha-<commit>`, and dispatches the image digest to
   `home-infra`'s `gitops-promote.yml` (needs the `HOME_INFRA_DISPATCH_TOKEN` secret).
3. `home-infra` writes the released manifests to its `gitops` branch, and Argo rolls them out.

Deployment templates live in `home-infra/k8s/apps/career-strategy`. Run `migrate` against
production before a release that adds migrations.

Locally, `make homelab-check` runs the release checks and `make homelab-build` builds the image.
Direct deployment and rollback are disabled to keep GitOps the only writer; roll back by
promoting an earlier tag.
