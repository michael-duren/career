# Leetgrinder

Leetgrinder tracks your LeetCode practice. Solve any problem you like on LeetCode; the app works out what the problem is and whether today's attempt is new, a review, or practice, holds you to a daily goal, and schedules reviews with spaced repetition. Open `/leetgrinder` after signing in.

> **Upgrading from the curriculum.** The 84-day curriculum is retired (see [`retired/leetgrinder/`](../retired/leetgrinder/README.md)). **Before deploying, download "Export attempt history"** from the side navigation. Migrations 019 and 020 keep every attempt, code and analysis; add the problem catalog (seeded with the curriculum's curated optimal complexities) and daily goals; drop the completed sessions, start date and daily hours; rewrite the reminder settings; and recompute which attempts are reviews. Day pages and `/leetgrinder/about` answer 410 Gone.

The side navigation links the dashboard, problems, reviews, stats and settings. Pages use the main site's zinc and blue palette.

## Daily goal

The goal is a number of new problems plus a number of reviews each day, 2 + 1 by default (about two hours). Set both targets, from 0 to 10 (not both 0), and the time zone under **Daily goal** in `/leetgrinder/settings`. All days are local dates in that time zone.

- An attempt is **new** if its problem has no attempt on an earlier local day. Several attempts on a new problem the same day count once.
- An attempt is a **review** if the problem has an attempt on an earlier day and was due by the end of the day (its FSRS due date, or a complexity flag), or was that day's review pick. Other re-solves are **practice**: shown, but not counted toward the goal.
- Unfinished attempts count: the goal is about time spent, not only solves.
- A day's **goal is met** when it has at least one attempt, the new target is reached, and the reviews reach the review target, capped at the reviews that could count that day (problems due or flagged, plus a reviewed pick). A day with nothing due is met by new problems alone. Work beyond the goal is **bonus**.
- Each day's targets are frozen in `leetgrinder_daily_goal` on first access that day (dashboard, API, or reminder worker), the same way review picks are. Changing the goal affects today only if today has not been frozen yet, otherwise from tomorrow; the settings page says which. Days before this feature count with 2 + 1.
- The **streak** counts consecutive goal-met days ending today, or ending yesterday while today's goal is still open. The dashboard shows it with the longest streak and a looser count of consecutive days with any attempt.
- **Changing the time zone recounts past days.** Frozen goals and review plans stay on their old local dates, but every attempt is placed on its date in the current zone, so late-evening attempts can move to another day and streaks can change. Submitting a different time zone shows a confirmation step first (no JavaScript needed) with the current streak, longest streak and goal-met days in the last 8 weeks in the saved and the new zone, and the goal that will be applied. The figures are read-only: today is planned in memory, nothing is saved or frozen. The zone and goals are saved only on confirm. A stale revision returns 409, and a preview that cannot be computed returns 503 with your draft kept. Saving only the goal, or the same zone, saves directly.

`is_review` on attempts is set by the server at save time (the problem has an attempt on an earlier local day); the client value is ignored.

**New problems from todos (optional).** Tick "Pick today's new problems from my todos" under **Daily goal** to have each day pick as many new problems as its new target from your todos. Picks are the oldest todo entries still to do whose problem has no attempt before that day (so an attempt on it counts as new); a problem queued in several places is offered once, from its oldest entry still to do. Like review picks, a date's picks are frozen in `leetgrinder_new_plan` when first needed (dashboard, API, logging an attempt, or reminder worker), and a frozen pick is never removed or replaced that day, even if its todo is removed. A day short of its target, because too few todos could be picked, adds picks if todos are queued, or the option is turned on, later that day; while the new target is not met, the goal card says todos already done, or attempted on an earlier day, are skipped. Planning new picks is optional: if it fails, the goal and review picks are still saved, the error is logged, the goal card (while the new target is not met), the morning plan notification and the today API (`newPicksFailed`) say the picks could not be made, and the next access tries again. A changed new target applies from the day after today's goal is frozen, as for the goal itself. Turning the option off hides frozen picks and stops new ones; it is off by default (`leetgrinder_settings.new_from_todos`, migration 029), and todos, the goal and review picks work the same either way. Any new problem still counts toward the goal, not only the picks. The goal card lists today's picks with their set and, while the new target is not met, names the next one, for example "Next new problem: Two Sum from Blind 75"; the morning plan notification lists them as "New: Two Sum (Blind 75)"; and `GET /api/leetgrinder/today` returns them as `newPicks`. Deleting a todo set keeps picks already frozen from it, shown without the set name.

The dashboard shows today's goal card (new x/n, review x/n, bonus, met, and today's new picks when picking from todos is on), the streak, today's review pick(s) with a reason and a form to log them, the optional "Also due" list (top 10), a **Log an attempt** form that takes a LeetCode or NeetCode URL, or a LeetCode slug, and opens its page, recent attempts, and all-time totals.

**Problem references.** The Log an attempt form, todo sets and the MCP todo tools take a problem as a `leetcode.com` or `leetcode.cn` URL (same slugs; `www.`, a trailing `/description/` or similar path, and query strings are fine), a `neetcode.io/problems/{slug}` URL, a `/problems/{slug}` path, or a bare LeetCode slug. A NeetCode slug is mapped to the LeetCode slug it mirrors (`two-integer-sum` is `two-sum`) through `internal/leetgrinder/neetcode_slugs.json`, which the extension's `neetcode-slugs.js` is generated alongside (`node scripts/update-neetcode-slugs.js` writes both, and a Go test fails if they differ). A NeetCode slug missing from the table is rejected with "no known LeetCode match" instead of guessed. A bare slug is always read as a LeetCode slug, so `two-integer-sum` alone is not mapped.

## Problems

Any LeetCode problem can be tracked. `leetgrinder_problems` caches each problem's number, title, difficulty, LeetCode topic tags, and optimal complexity. The retired curriculum's 300 problems are seeded after every migration from `internal/leetgrinder/catalog_seed.json` with curated optimal values; any other problem gets a row when its first attempt is saved. Metadata comes from:

1. The extension, which reads it same-origin from LeetCode's GraphQL API and sends it with `PUT /api/leetgrinder/problem/{slug}` or with the attempt. The server validates it (title required, lengths, difficulty, at most 20 slug-shaped tags) and never replaces known values with empty ones or touches optimal values.
2. A background fetcher that asks `https://leetcode.com/graphql` for one problem a minute: rows without a title, and seeded or extension-saved rows with attempts but no tags (the extension saves NeetCode problems without topics and leaves them queued). Each request times out after 10 s; failures retry after 1, 10 and 60 minutes, then stop. A problem LeetCode does not know is marked "Not found on LeetCode". If LeetCode blocks server requests, metadata relies on the extension and pages show the slug until then.

Topic display names come from LeetCode (`topics:[{slug,name}]`), so "depth-first-search" shows as "Depth-First Search". They are kept in `leetgrinder_topics(slug, name)`, upserted whenever the extension or the background fetcher saves metadata; an empty name never replaces a stored one, and a handful of common tags are backfilled by migration 028. Names for tags beyond the backfilled ones arrive on the next metadata save that includes them (an extension visit or the background fetcher). Tags known only by slug (for example topics sent through the MCP todo tools) are labelled by title-casing the slug until a name arrives. The same label is used on the problems page and its topic filter and search, the stats page, and todo sets.

`/leetgrinder/problems` lists every attempted problem with its number, title with its topics as tags below it, difficulty, optimal time and space ("Claude's estimate" when estimated), latest result (with the best result below it when it differs), attempts, last attempt, next due, and a LeetCode link. Search matches title, slug and topic, and a bare number matches that LeetCode number exactly; filters narrow by difficulty, topic (including Untagged), and status (due, flagged, ever solved, solved last time, needed help last time, struggled last time, unfinished last time); sorting is by last attempt, next due, number, title, difficulty, or recall. Filters live in the URL. A problem's page (`/leetgrinder/problem/{slug}`) works for any valid slug and shows its metadata, latest and best result, recall, next due and flag reason above the attempt history.

**Latest and best result.**

- The *latest result* is the newest attempt's outcome: Solved independently, Solved with help, Struggled or Unfinished.
- The *best result* is Solved independently if any attempt was an unassisted solve, else Solved with help if any attempt was a solve, else Not solved. It is shown (below the latest on the table, beside it on the problem page) only when it is a solve that differs from the latest, so a problem solved in March and left unfinished in October reads Unfinished, best Solved independently.
- Status filters: "Ever solved" (key `solved`, the best result), "Solved last time" (latest was a solve, with or without help), "Needed help last time" (latest was Solved with help, which still flags the problem for review), "Struggled last time" and "Unfinished last time".
- **Changed meaning:** `status=struggled` and `status=unfinished` now match the latest result, not the old combined status. Bookmarked URLs keep working but can list different problems: one solved long ago and unfinished since now appears under Unfinished as well as Ever solved.
- The stats page, extension API, dashboard totals and MCP tools do not use these labels and are unchanged.

## Reviews

Every attempted problem becomes a review card. Card state is never stored: each request replays the problem's attempts through FSRS ([go-fsrs](https://github.com/open-spaced-repetition/go-fsrs) v4, default weights and 90% desired retention), so corrections change due dates immediately. Unfinished rates Again. Struggled, or solved with help, rates Hard. An unassisted solve over 25 minutes rates Good, and 25 minutes or less rates Easy. Only the last attempt on each local day counts. FSRS's minute-scale learning steps are turned off, since reviews happen at most once a day. Every attempt feeds FSRS, practice included.

**Complexity flag.** When a problem's latest attempt has a completed analysis that judged a stated complexity wrong, or the solution not optimal, the problem is due the day after the analysis finished (or at its FSRS due date, if earlier). The reason reads, for example, "Time complexity judged wrong 2 days ago" or "Not optimal: O(n²) vs O(n)". The next attempt on the problem, or a re-analysis without those verdicts, clears it.

**Struggles and your own flags.** A latest attempt that was a struggle (struggled, unfinished, or solved with help: the same struggles the stats page counts), marked "I want to review this problem again soon", or with the approach "Took a simpler approach for time" flags the problem the same way. It is due the day after the attempt first flagged it: the attempt's day, or the day a correction made it flag when it did not before (`marked_at`), so a later correction never turns past practice into reviews. Migration 023 dated the flags of struggles saved before struggles flagged from the migration, so past days kept their goals and streaks. The reason reads "Struggled 2 days ago" (always the attempt's own day), "Took a simpler approach 2 days ago" or "Marked for review yesterday" (the review pick and due list add the recall estimate to a struggle), and the badge "Flagged: struggled" and so on. An analysis verdict on the same attempt reads first with its own date, and the earlier of the two dates schedules the review. The next attempt clears it, as does a correction to an unassisted solve without marks; like a re-analysis, that can recount past days. "Reached the optimal solution" never flags.

**Daily picks.** Each date gets as many picks as its review target, the first time they are needed, frozen in `leetgrinder_review_plan`. Candidates are cards due by the end of the day that were not first attempted that day, ordered flagged first, then lowest estimated recall, then most overdue. Raising the target on a later day adds picks; lowering it never removes them. Any due problem counts toward the review goal, not only the picks. The other due cards form the optional due list; the **backlog** is due cards outside today's picks and not attempted today.

`/leetgrinder/reviews` lists every card with its due date, recall now, flag reason and today's pick marked, plus the backlog.

## Stats

`/leetgrinder/stats` shows, per LeetCode topic: problems attempted, solved, struggle rate (struggled, unfinished and assisted attempts over all attempts), average current recall, and how many are due. It is sorted weakest recall first by default and can sort by struggle rate, due count, problems, or topic. A problem counts under each of its topics; topics with fewer than 3 problems are grouped under "Other" unless "List topics with fewer than 3 problems" is ticked, and problems without metadata count as "Untagged". ## Notifications

Leetgrinder can send reminders to [ntfy](https://ntfy.sh). In `/leetgrinder/settings`, set the ntfy server URL (default `https://ntfy.sh`), a topic, and optionally an access token, then subscribe to the same topic in the ntfy app. Anyone who knows a public ntfy.sh topic can read it, so use a long random topic name or a protected topic with a token. "Send test notification" posts a test message with the saved settings and shows the result. An empty topic turns every notification off.

The token field is write-only. The page shows only "Token set" or "No token set"; leave the field blank to keep the saved token, or tick "Clear the saved token". Tokens are encrypted with AES-256-GCM before they are stored (see `LEETGRINDER_SECRET_KEY` below) and never appear in pages, logs, or notification errors. Changing the server to a different host requires re-entering or clearing the token, so a saved token is only ever sent to the server it was entered for.

Each reminder can be turned on or off and has its own time, priority, and, where it applies, threshold:

| Reminder | Default | Sends when |
|---|---|---|
| Morning plan | on, 08:00 | Always: today's targets, today's new picks from todos (when on), the review pick(s), how many more are due, and the current streak. |
| Goal incomplete | on, 18:00 | Today's goal is not met. Lists what is left, for example "1 new, review: Two Sum". |
| Streak at risk | on, 21:00, high priority, threshold 1 | The goal is not met and the current streak is at least the threshold in days; 0 sends whenever the goal is not met. |
| Review backlog | off, 18:00, threshold 10 | At least the threshold number of due reviews are outside today's picks. |

A worker inside the server checks once a minute, in the settings time zone. Each reminder is evaluated once its time has passed and sends at most once per local date; if its condition is not met at that point it is logged as "Nothing to send" and not checked again that day. Enabling a reminder after its time has passed evaluates it on the next tick, but only inside its lateness window: 4 hours for the morning plan and 2 hours for the others. A reminder found later than that, for example after the server was down, is logged as "Too late to send (past its window)" and not sent. This also happens when you enable a reminder or move its time earlier after the window has passed. A failed or abandoned send that is retried after its window is skipped too, and the log keeps its last error: "Too late to send (last error: ...)". Reminders run whenever a topic is set. Notifications carry a title, priority, tags, and a click link to the dashboard (or the review queue for the backlog), built from `PUBLIC_ORIGIN`. Log rows from the retired reminders (Missing work, Behind schedule, Late escalation) keep their names.

Every send is recorded in `leetgrinder_notification_log`, keyed by reminder and local date. The worker claims a row with `INSERT ... ON CONFLICT` before sending, so ticks and restarts never double-send. A failed send is logged with the error and retried on a later tick at least five minutes apart, up to three retries (four attempts) that day. A send interrupted by a crash is retried the same way. Settings show the latest 14 log rows, including test sends.

## Attempts

Record each attempt as solved, struggled, or unfinished, with minutes spent, whether you used a hint or reviewed a solution, and the time and space complexity of your solution. A solve means the solution passed on LeetCode. Two optional self-assessments flag the problem for review (see Reviews): the approach (not stated, "Reached the optimal solution", or "Took a simpler approach for time") and "I want to review this problem again soon". Both show in the attempt history, can be corrected, and are stored as `approach` (`''`, `optimal` or `suboptimal`) and `wants_review`, with `marked_at` recording when the first mark was raised.

Complexity is a select of common classes, stored exactly as shown (`O(1)`, `O(log n)`, `O(√n)`, `O(n)`, `O(n log n)`, `O(n²)`, `O(n³)`, `O(2ⁿ)`, `O(n!)`), or "Other…" with free text such as `O(m·n)`, `O(V + E)` or `O(k log n)`. Other values are trimmed, must start with `O(` and end with `)`, and fit in 40 characters. Runs of spaces collapse to one, and `n^2`, `n^3`, `2^n`, `nlogn` and `logn` become `n²`, `n³`, `2ⁿ`, `n log n` and `log n`. Both values are required for solved and struggled attempts, including corrections of them, and optional for unfinished ones. The form works without JavaScript (the text field is always shown, and counts when "Other…" or nothing is selected); a small script hides it until "Other…" is chosen. One Go validator (`internal/leetgrinder/complexity.go`) enforces these rules for the form, the API, and storage; the extension mirrors it in `lib.js`, and both run the vectors in `extension/leetgrinder/test/complexity-vectors.json`.

Attempts logged by the extension can carry the code LeetCode judged and its language, capped at 64 KiB. The attempt history shows the stated complexities, and the code, escaped, in a collapsed "Submitted code" block with its language and size. Corrections change the stated complexities but keep the captured code. Web-logged attempts have no code. The dashboard counts distinct solved problems and independent solves separately. History retains repeated attempts. Attempt times are shown in the settings time zone, and a re-solve is labelled Review or Practice by how its day counted it (the same rule as the dashboard), not by the flag stored when it was saved. Use “Correct this attempt” to fix an entry; concurrent corrections cannot silently replace one another. A problem's attempt history page shows its optimal time and space complexity once you have logged at least one attempt; before that it says the values appear after your first attempt. The 300 problems of the retired curriculum have curated values (see the retired [sources and verification](../retired/leetgrinder/docs/leetgrinder-sources.md#optimal-complexity-table)); other problems get Claude's estimate from their first analysed attempt, labelled "Claude's estimate".

**Fixing the optimum.** The problem page's "Optimal complexity" panel (shown after the first attempt) labels the source: "Curated", "Claude's estimate" or "Your value". "Edit optimal complexity" (`GET`/`POST /leetgrinder/problem/{slug}/optimal`) takes an optimal time, an optimal space (both required, through the same normaliser as stated complexity) and a note of up to 300 characters, and stores them with `optimal_source = 'manual'` (migration 027 allows the value). It may replace a model estimate, a curated value or an earlier manual one. Estimates fill only an empty optimum and the catalog seed never replaces a row, so a manual or curated value is never overwritten. "Re-estimate" (`POST .../optimal/reestimate`, offered only for a model estimate) clears a `model` value and nothing else (a curated or manual value answers 409), so the next analysis estimates again. It does not requeue an attempt: analysis may be off, paused or at its daily limit, and requeueing discards an attempt's result. Existing verdicts keep judging against the value they saw until an attempt is re-analysed (use Re-analyse on the latest attempt). Both forms are same-origin, form-encoded posts that carry a revision (a hash of the optimum's source and values); a form opened before a model estimate, an edit or a re-estimate is refused with 409 and, for the edit, keeps the draft. The edit refusal shows the current value beside your draft and carries the current revision, so saving again is a deliberate overwrite. A problem with no attempts answers 404 for both forms (the optimum stays hidden and no catalog row is created). Re-estimate redirects back with a note that the next analysed attempt, or Re-analyse, estimates the optimum again. A save redirects back to the panel.

Use “Export attempt history” to download Leetgrinder history as JSON: `attempts` (each with `timeComplexity`, `spaceComplexity`, `code`, `codeLanguage`, `wantsReview`, `approach` and `markedAt`), `problems` (catalog rows of attempted, review-planned and todo problems; a slug with no catalog row is left out), `dailyGoals` (each day's frozen targets), `reviewPlans` (each date's frozen review picks, in slot order, which past day kinds and streaks depend on), `todos` (`sets` with title, description, metadata, creation time and their `items`, plus standalone `items`; each item has its problem slug, source data and creation time) and `settings` (time zone, daily goal, ntfy URL and topic, reminder preferences, the analysis toggle and `newFromTodos`). Frozen new-problem picks are not exported: they do not change how any day counts. The ntfy token and its ciphertext are never exported, so set the token again after a restore. Treat an export as private: on a public server such as ntfy.sh the topic name is effectively a secret, so do not share or publish an export. `version` is 2: version 2 added `reviewPlans`, `todos` and `settings`, and later additions of new fields keep it, while removing a field or changing its meaning bumps it. An export with no `version` is the earlier format, without `reviewPlans`, `todos` and `settings`. The export is a history record, not a full backup: it leaves out analysis verdicts (derived data), API tokens, the notification log, todo item IDs, done state (derived from attempts), todos' imported problem metadata and catalog `metadata_source`; PostgreSQL backups remain the full restore mechanism. All sections are read in one database snapshot. This is separate from the existing workspace archive. There is no Leetgrinder import UI yet.

## Complexity analysis

When the server has an Anthropic API key, a background worker asks Claude to assess each attempt that has captured code and at least one stated complexity. The attempt history shows a "Claude's assessment" card under the code: the actual time and space complexity, a ✓ or ✗ against each stated value, whether the solution is optimal, and a short explanation. The problems table (for the latest attempt) and the dashboard's recent attempts show a "Check complexity" badge when a stated value was judged wrong. A verdict of a wrong stated value or a non-optimal solution also flags the problem for review the next day (see Reviews). The assessment can be wrong for subtle amortised or input-dependent cases; your stated values are never changed.

The request carries the problem's title, number, slug and link, the language, the code, your stated time and space, and the problem's optimal time, space and note when the catalog has them. Without them, the request asks Claude to estimate the optimum as well (`optimalTime`, `optimalSpace`, and a one-line `optimalNote`); the estimate is normalised and stored on the problem with `optimal_source = 'model'`, only if the problem has none yet, and curated values are never replaced. The optimum is a reference: when its note says the usual interview solution is slower than the best-known bound (Fibonacci by matrix exponentiation, for example), a solution that reaches that accepted optimum still counts as optimal. The code is fenced by a random boundary, and the model is told to treat it as untrusted data, so instructions hidden in comments or strings are ignored. The response must match a JSON schema (structured output); the server then accepts only the schema's fields, requires both complexities to pass the same normaliser as stated values, drops a match verdict for an unstated value, and caps the explanation at 2,000 characters. Everything is rendered escaped.

Analyses live in `leetgrinder_analyses`, one row per attempt, keyed to a SHA-256 of the analysed inputs (language, stated time, stated space, and code). The attempt stores the current hash in `leetgrinder_attempts.input_sha256`, which a trigger computes on insert and recomputes on any update that changes one of those inputs, so the worker, the queue counts and every dashboard or extension request compare stored hashes instead of rehashing each attempt's code. Correcting a stated complexity changes the hash and queues the attempt again. The worker ticks once a minute, sends one request at a time (a PostgreSQL advisory lock keeps it to one across replicas), and handles the newest attempts first. A failed request ends the tick, so an outage costs at most one request a minute, and is retried after 1, 4 and 9 minutes, up to four requests in all. Refusal and truncation errors fail at once. Errors that would hit every attempt pause all workers for 15 minutes; the pause is stored in `leetgrinder_analysis_pause`, so it holds across restarts and replicas, and settings show it with its reason. Configuration errors (401, 402, 403 or 404: a bad key, billing, permissions or model) also leave the attempt pending without using a try, so fixing the environment needs no re-analyse. A 400 (for example a model that does not support the request, or no credit) pauses too but counts as a try, so a single bad attempt cannot block the queue. Stored errors keep only the HTTP status and error type, with the key redacted, never a request or response body. "Re-analyse" on the card resets the analysis to pending (a same-origin form post). Analyses are derived data and are not exported.

Configuration (environment only):

| Variable | Default | Meaning |
|---|---|---|
| `ANTHROPIC_API_KEY` | empty | Enables analysis. Never stored in the database, logged, or shown; settings show only whether it is configured. |
| `LEETGRINDER_ANALYSIS_MODEL` | `claude-sonnet-5` | Model ID. |
| `LEETGRINDER_ANALYSIS_DAILY_LIMIT` | `50` | Requests per local day in the settings time zone, counting retries. `0` sends none. |

The **Complexity analysis** section on `/leetgrinder/settings` shows whether a key is configured, the model, today's requests against the limit, and queue counts, with a toggle that defaults to on (stored in `leetgrinder_settings.analysis_enabled`). Settings are read before every request, so turning it off stops the next one; queued attempts wait. While analysis is off or no key is configured, attempt cards say so and hide "Re-analyse". Without a key the worker never makes a network call.

Cost: each request uses adaptive thinking at medium effort with output capped at 16,000 tokens (thinking plus the answer), and each request times out after five minutes. At Claude Sonnet 5's list price ($2 per million input tokens, $10 per million output tokens), a typical attempt costs about one to two cents; the worst case, 64 KiB of code and a full output, is about 20 cents. The default daily limit therefore bounds spending at roughly $10 a day, and far less in practice. Check current pricing before raising the limit or choosing a larger model.

Privacy: your captured code, with the problem and your stated complexities, is sent to Anthropic only while a key is configured and the toggle is on. Anthropic's API data-retention terms apply to those requests. Web-logged attempts have no code and are never sent.

## Browser extension

`extension/leetgrinder/` is a Manifest V3 extension (version 2.3.0) for Chrome and Firefox. On every `leetcode.com/problems/{slug}/` page, and on every `neetcode.io/problems/{slug}` page for a problem that mirrors a LeetCode problem, it times the attempt (active time only: the tab must be visible and you must have used the keyboard, mouse or scroll within the last 10 minutes, so a long break with the tab open stops counting after the 10-minute window, which also covers thinking time without typing; several tabs on one problem count once; a backward clock step keeps open time continuous, and a forward step over 30 minutes expires the timer like sleep), shows a banner with the problem's status ("New", "Review due · recall 62%", "Today's review", "Flagged: …", or "Reviewed 3 d ago · next due Oct 14"), and, when a submission is Accepted, opens a confirm panel prefilled with the outcome (solved at 25 active minutes or less, otherwise struggled), the active minutes (with "Active N min (open M min)" when they differ), and whether you opened the Solutions or Editorial tab (Solution on NeetCode). NeetCode attempts are logged under the LeetCode slug, so both sites share one history. The panel says how the attempt will count ("New", "Review" or "Practice"), asks for time and space complexity (required for solved and struggled), whether you reached the optimal solution or took a simpler approach for time, and whether you want to review the problem again soon, and attaches the judged code unless you untick it. Nothing is sent until you confirm. After 25 active minutes without an Accepted submission it offers to log the problem as unfinished. The toolbar badge shows what is left of today's goal (a ✓ when met), and the popup shows today's progress, streak, picks and due list. See the [extension README](../extension/leetgrinder/README.md) for loading it unpacked and the manual test checklist.

The extension authenticates with a personal API token. Create one under **Browser extension tokens** on `/leetgrinder/settings`. The token (`lg_` plus 32 random bytes in base64url) is shown once, in the response to the create request; only its SHA-256 hash is stored in `leetgrinder_api_tokens`. The list shows each token's name, creation time, last use (recorded at most once a minute), and revocation. Revoked tokens are rejected immediately. At most 20 tokens can be active.

API, authenticated only with `Authorization: Bearer <token>` (session cookies are ignored; `/api/` bypasses the login redirect, so these handlers check the token themselves):

- `POST /api/leetgrinder/attempts` with JSON `{id, problemSlug, outcome, minutes, assisted, notes, timeComplexity?, spaceComplexity?, code?, codeLanguage?, wantsReview?, approach?, problem?, isReview?}`. It uses the same idempotent attempt creation as the web form and records `source = 'extension'`. `problem` is optional metadata `{number, title, difficulty, topics:[{slug,name}]}`, stored in the same transaction (invalid metadata is dropped, not an error). `isReview` is accepted and ignored. The response is `{attempt, kind}` with `kind` `new`, `review` or `practice`. Retrying with the same `id` and values returns the saved attempt; the same `id` with different values is `409`. Other responses: `401` bad or revoked token; `422` complexity missing on a solved or struggled attempt, or not in `O(...)` form; `400` invalid fields or JSON; `413` code over 64 KiB or body over 96 KiB; `415` non-JSON body. `approach` must be `optimal`, `suboptimal` or empty (`400` otherwise); `wantsReview` defaults to false. Retrying with the same `id` compares both. The extension leaves both out when unset.
- `GET /api/leetgrinder/problem/{slug}` returns `known` and metadata when known, `status` (`new`; `due` with `recall`, `dueDate` (today when the problem is due only as today's pick), `flagReason?`; or `notDue` with `nextDue`), `todaysPick`, `lastAttemptedAt`, `attemptedToday`, `todayKind`, `latestAttempt` (without code) and `historyUrl`.
- `PUT /api/leetgrinder/problem/{slug}` with `{number, title, difficulty, topics:[{slug,name}]}` stores metadata; `204` on success.
- `GET /api/leetgrinder/today` returns `{date, goal:{new, review}, done:{new, review, bonus}, met, remaining, streak, picks:[{slug,title,difficulty,recall,reason,done}], newPicks:[{slug,title,difficulty?,set?,done}], newPicksFailed?, due:[…, at most 20], dueCount}`. The review goal is the capped target. Like the dashboard, it freezes today's goal and picks on first access.

## Development

The feature uses Go templ, not Astro or a client-side editor. The templ generator and runtime are pinned together in `go.mod`. Run:

```sh
make generate
make build
make test
make test-postgres
cd extension/leetgrinder && node --test
```

`make dev` generates templates before starting Go. Docker builds generate them too. Generated `_templ.go` files remain ignored, so run `make generate` before invoking `go test ./...` directly in a fresh checkout. `retired/` is a separate stub Go module with `*.templ.retired` templates, so builds, tests and `templ generate` skip it.

Leetgrinder pages require the existing login. Writes use same-origin HTML forms with server validation. Failed attempt saves display the submitted draft for retry. Attempt IDs prevent duplicate creates; revisions protect corrections. Tracking belongs to the app's existing single configured account.

The ntfy access token is stored encrypted with AES-256-GCM. Set `LEETGRINDER_SECRET_KEY` to 32 random bytes encoded as base64 (for example `openssl rand -base64 32`). Development derives a key from `JWT_SECRET` when it is unset. In production, `serve` refuses to start without the key once an encrypted token is stored. Changing the key makes a stored token unreadable, so re-enter the token afterwards.
